# AI 本地路线智能规划系统 MVP

这是一个基于 Flask + Leaflet 的本地路线智能规划系统 MVP。

当前版本聚焦于“核心路线引擎模块”：用户输入起点、偏好、预算、排队限制、游玩时长等条件后，系统基于杭州 Mock POI 数据生成三种路线方案，并在网页中展示路线卡片和地图路线。

## 1. 当前版本功能

当前 MVP 已实现：

- 用户输入起点坐标与出行偏好
- 使用杭州 Mock POI 数据
- POI 过滤：预算、排队时间、营业时间、距离范围
- POI 评分：评分、偏好匹配、排队时间、价格、历史偏好标签
- 贪心路线生成：综合考虑评分与地理连贯性
- 三方案输出：
  - 需求满足方案
  - 硬约束方案
  - 历史偏好洞察方案
- POI 数量支持两种模式：
  - 用户不填写时，系统根据游玩时长动态计算
  - 用户填写时，作为硬约束处理
- 路线执行细节：
  - POI 顺序
  - 到达时间
  - 离开时间
  - 路段距离
  - 路段交通时间
  - 总花费
  - 总耗时
- Flask API 路线生成接口
- Web 页面三方案卡片展示
- Leaflet 地图展示起点、POI 标记和路线连线
- 基础异常处理：
  - 起点坐标格式错误
  - 约束过严无法生成路线
  - 指定 POI 数量无法满足

## 2. 暂未实现功能

- 真实美团 / 高德 / Google Places 等 POI API 接入
- 真实 LLM API 接入
- 用户登录
- 用户历史数据持久化
- 朋友中心选址

## 6. 使用方式

打开网页后，可以填写或修改以下内容：

- 起点坐标，例如：`120.1551,30.2741`
- 用户意图，例如：`周末想在杭州轻松逛逛，吃点本地特色`
- 菜系偏好，例如：`杭帮菜`
- 偏好标签，例如：`本地风味,放松`
- 预算上限
- 最大排队时间
- 开始时间与结束时间
- 预计游玩时长
- 出行方式
- 希望 POI 数量

其中，“希望 POI 数量”是可选项：

- 不填写时，系统会根据预计游玩时长自动计算 POI 数量；
- 填写时，系统会将其作为硬约束；
- 如果当前预算、时间、距离或排队条件无法满足指定 POI 数量，对应方案会返回失败提示。

点击“生成路线”后，页面会展示三种方案：

- 需求满足方案
- 硬约束方案
- 历史偏好洞察方案

每张方案卡片会展示：

- 路线简介
- POI 数量
- 总耗时
- 总花费
- POI 顺序
- 各段交通信息

点击“在地图中查看”后，下方 Leaflet 地图会展示该方案的起点、POI 标记和路线连线。

## 7. API 接口说明

### 7.1 路线生成接口

```text
POST /api/generate_route
```

该接口接收用户输入的起点、偏好、预算、时间窗口、排队限制、游玩时长等信息，并返回三种路线方案。

### 7.2 示例请求

```json
{
  "start": "120.1551,30.2741",
  "user_input": "周末想在杭州轻松逛逛，吃点本地特色",
  "preferences": {
    "city": "杭州",
    "food": ["杭帮菜"],
    "tags": ["本地风味", "放松"],
    "budget": 300,
    "time_window": ["10:00", "18:00"],
    "max_wait": 30,
    "duration_minutes": 240,
    "transport": "walk"
  }
}
```

### 7.3 示例返回结构

```json
{
  "success": true,
  "message": "三方案路线生成完成。",
  "city": "杭州",
  "start_point": {
    "lng": 120.1551,
    "lat": 30.2741
  },
  "preference_insight": {
    "inferred_intent": "用户可能希望进行低压力、轻松探索型出游。",
    "favorite_cuisines": ["杭帮菜", "川菜", "咖啡", "茶饮"],
    "discovered_preferences": ["散步", "本地风味", "小众", "朋友聚餐", "适合聊天", "放松", "安静"]
  },
  "options": [
    {
      "type": "demand_satisfaction",
      "success": true,
      "message": "路线生成成功",
      "route": {
        "start_point": {
          "lng": 120.1551,
          "lat": 30.2741
        },
        "pois": [],
        "segments": [],
        "total_cost": 0,
        "total_time": 0,
        "total_travel_time": 0,
        "total_distance": 0,
        "search_radius_km": 0,
        "option_type": "demand_satisfaction",
        "summary": ""
      },
      "summary": "",
      "summary_valid": true
    }
  ]
}
```

### 7.4 方案类型说明

| type | 中文名称 | 含义 |
|---|---|---|
| `demand_satisfaction` | 需求满足方案 | 优先满足用户输入需求，可以适度放宽部分条件 |
| `hard_constraint` | 硬约束方案 | 严格满足预算、排队、时间、距离等约束 |
| `preference_insight` | 历史偏好洞察方案 | 基于 Mock 用户偏好进行规则模拟推荐 |

### 7.5 异常返回示例

当起点坐标格式错误时：

```json
{
  "success": false,
  "message": "起点坐标格式错误，请使用 lng,lat 格式，例如 120.1551,30.2741",
  "options": []
}
```

当约束过严，三种方案均无法生成时：

```json
{
  "success": false,
  "message": "当前条件下无法生成可用路线，请调整预算、时间、排队限制或 POI 数量。",
  "options": [
    {
      "type": "demand_satisfaction",
      "success": false,
      "message": "当前条件下无法满足指定 POI 数量，请放宽预算、时间或排队限制，或减少 POI 数量。",
      "route": null,
      "summary": "当前条件下无法满足指定 POI 数量，请放宽预算、时间或排队限制，或减少 POI 数量。"
    }
  ]
}
```

## 8. 核心设计说明

### 8.1 Mock 数据策略

当前版本使用 `data/mock_pois.json` 中的杭州 Mock POI 数据，不接入真实平台 API。

Mock POI 数据包含：

- POI 名称
- POI 类型
- 经纬度
- 菜系或标签
- 评分
- 人均消费
- 排队时间
- 停留时长
- 营业时间
- 适合人群
- 热度

这些字段主要用于验证核心路线引擎的过滤、评分和路线生成逻辑。

后续如果接入真实 POI API，优先修改：

```text
services/poi_service.py
```

核心路线引擎 `route_engine.py` 不直接关心数据来自 Mock 文件还是真实 API。这样可以降低后续接入真实数据时的重构成本。

### 8.2 LLM 预留策略

当前版本不接入真实 LLM。

历史偏好洞察方案使用规则模拟方式生成，主要基于：

- Mock 用户历史偏好
- 用户偏好标签
- 历史访问类型
- 避免访问的 POI
- 偏好的场景标签

后续如果接入真实 LLM，优先修改：

```text
services/llm_service.py
```

未来可以将以下信息作为 LLM 输入：

- 用户自然语言需求
- 用户历史偏好
- 候选 POI 数据
- 当前路线方案
- 预算、时间、排队等限制

然后由 LLM 完成：

- 意图补全
- 偏好挖掘
- 推荐理由生成
- 安全边界校验

### 8.3 地点范围约束

当前版本没有采用固定距离作为地点范围，而是根据以下字段动态推导：

- `duration_minutes`：预计游玩时长
- `transport`：出行方式

基本逻辑是：

- 游玩时间越短，推荐范围越小；
- 步行模式下推荐范围较小；
- 骑行模式下推荐范围适中；
- 驾车模式下推荐范围更大。

这样可以避免简单写死“8 公里以内”带来的不合理结果。

### 8.4 POI 数量约束

POI 数量采用可选策略：

- 用户不填写时，系统根据游玩时长动态计算；
- 用户填写时，系统将其作为硬约束；
- 如果某个方案无法满足指定 POI 数量，该方案返回失败；
- 如果三种方案全部失败，整体 `success=false`。

该设计用于同时满足：

- 用户希望明确控制路线长度；
- 用户不确定时由系统自动规划；
- 约束过严时给出明确错误提示。

### 8.5 三方案生成逻辑

当前版本同时生成三种方案。

需求满足方案：

- 更重视用户输入需求和体验质量；
- 可以适度放宽预算和排队限制；
- 更适合展示“体验优先”的路线。

硬约束方案：

- 严格控制预算、排队、营业时间和距离；
- 更适合展示“稳定、可执行”的路线。

历史偏好洞察方案：

- 当前基于 Mock 用户偏好进行规则模拟；
- 优先考虑用户偏好的标签和历史行为；
- 后续可以替换为真实 LLM 洞察。

### 8.6 路线生成策略

当前路线生成使用贪心策略：

1. 读取候选 POI；
2. 根据预算、排队、营业时间、动态范围等条件过滤 POI；
3. 根据评分、偏好、价格、排队时间计算综合分；
4. 从当前位置出发，优先选择综合分较高且地理距离较近的 POI；
5. 持续选择下一个 POI，直到达到时间限制或 POI 数量限制。

当前版本使用经纬度直线距离进行估算，不接入真实导航距离。

### 8.7 地图展示策略

当前版本使用 Leaflet 展示地图，并通过 CDN 在线引入。

地图展示方式：

- 页面下方设置一个公共地图区域；
- 三张方案卡片中都有“在地图中查看”按钮；
- 点击不同方案后，地图会切换显示对应路线；
- 地图展示起点、POI 标记和路线连线。

当前使用 OpenStreetMap 作为地图底图。

## 9. 当前版本边界

当前项目是 MVP 原型，重点验证核心路线引擎和产品闭环。

当前版本不代表真实美团数据，也不提供真实导航服务。所有 POI 坐标、价格、排队时间、热度等均为 Mock 数据，仅用于算法验证和产品演示。

当前暂未实现：

- 真实美团 API 接入
- 真实高德 / Google Places API 接入
- 真实 LLM API 接入
- 用户登录
- 用户历史数据持久化
- 朋友中心选址
- 盲盒路线
- 真实导航路径规划
- 实时排队数据
- 真实交通时间估算
- 线上生产环境部署
- Vue / React 等复杂前端框架

## 10. 后续开发方向

后续可以继续扩展以下能力：

### 10.1 真实 POI API 接入

将 `services/poi_service.py` 中的 Mock 数据读取替换为真实 POI API 请求，并完成字段映射。

### 10.2 真实 LLM 接入

将 `services/llm_service.py` 中的规则模拟逻辑替换为真实 LLM 调用，用于意图补全、偏好挖掘和推荐理由生成。

### 10.3 用户历史偏好系统

增加用户行为数据，例如：

- 历史浏览
- 历史收藏
- 历史到店
- 历史路线选择
- 不喜欢的 POI 类型

用于提升历史偏好洞察方案的推荐质量。

### 10.4 朋友中心选址

根据多个用户的起点或地标，计算几何中心点，并以该中心点作为路线起点。

### 10.5 盲盒路线

增加 citywalk、吃吃喝喝、文化之旅、旅游必去等主题路线，并通过随机机制生成惊喜路线。

### 10.6 真实路径规划

接入地图路径规划 API，替代当前的直线距离估算，使路线时间和距离更接近真实出行情况。

### 10.7 Leaflet 本地化

当前 Leaflet 使用 CDN 在线引入。后续可以将 Leaflet 的 JS、CSS 和图标资源下载到本地，提高演示稳定性。

### 10.8 线上部署

后续可以将项目部署到 Render、Railway、Vercel、云服务器等平台，并在 GitHub README 中补充在线 Demo 链接。
